# Build a phone agent from a brief

You are the builder. Input: one or more brief files, a tool API file (OpenAPI JSON), a slot name, and sometimes a cases file for practice. Output: `out/gen_<slot>.py` (your generator), `out/<slot>.workflow.json` (what it emits), saved on Freya under the slot. Work from the repo root.

**Freya can answer 5xx for minutes at a time** (500, 503 'API key validation is temporarily unavailable', 504): run the same call again after 30 s (save, chat turn, export), never create a new workflow or slot because of it, and do not count a 5xx test turn as an agent failure.

Use ONLY what the given brief(s) and tool API file say. Never copy a rule, value, date, name, enum or sentence from another brief, from the reference generators, or from memory. Hidden briefs differ from the kit's in every dimension: identity questions, wrong-answer limits, calendars and holidays, bands and deadline formulas, floors, attempt counts and proposals, outcome/reason tables, verbatim sentences, callback windows, tool fields and enum values. Customers can have one to three products. A brief can be raw material (a mail, a policy extract, a memo that changes it, a code list): a later document overrides an earlier one; apply the rule in force.

## 0. Before anything: case type, documents, language (decide in the first minutes)

Write at the top of `out/gen_<slot>.py`, before any code: `# CASE TYPE: collections | service`, `# LANGUAGE: <the language of the calls>`, `# CALL VARIABLES: <names the documents say every call carries>`, then a `# DECISIONS` block (below).

**Case type**, from the rule inventory's categories/topics, the tool API's operations and the example conversations:
- **collections**: the bank calls a customer about a debt (identity questions, a promise to pay, an outcome table for close_call). Follow the Procedure below as it is (`builder/policy.py`).
- **service line**: the customer called in, identity was done before the agent (phone menu / IVR) and arrives as call variables, the agent looks data up, reads it out, performs small service requests and transfers to a person for what it does not handle. Do NOT use `policy.Policy`, the identity helpers (`verify_post`, `opening_no_answer`, `reroute_not_customer`, `third_party_callback`, `gated_digits_identity`), `normalise_pre`, `spec.json`'s collections fields (bands, floors, ladder), `cases.py` or `sim.py`. Build the graph in "Service lines" below; from the Procedure keep steps 1-2 (reading; FREYALIB.md only), 4's platform rules (initial conversation node, no `test_variables`, `assemble()` checks), 5, 6, 8 and 10; steps 7 and 9 are replaced by "Self-tests without practice cases".

**Raw material: read every document, decide what is in force.** The brief can be the combined text of a case folder (`out/<slot>.case.md`: every file under its path header; PDF/docx/mail converted). Read ALL of it with Read in chunks (offset/limit), never by grep or a summary; open yourself every file the case note lists as not converted (Read opens PDFs and images; a flow drawing is a routing spec). Then:
- List the documents with their dates and versions (mail dates, v1/v2/v3, meeting dates). Per topic the rule in force is the LATEST dated decision, even when nobody writes "this replaces" (a meeting note after an analysis version overrides it; an earlier version of the same document is history; distractors brush the topic and decide nothing). Two data-model versions: the later one; but field names, paths, methods, enums and response shapes come from the tool API file only (it is what the mock answers).
- The example conversations show what is scored: follow their order of steps, what is read out and how (amounts, currencies, dates), tone, length and closing. Where an example and a dated decision disagree, check which is later and note the choice in DECISIONS.
- Phone-menu announcements, FAQ answers and fixed texts are verbatim lines: copy them in their original language, character for character.
- `# DECISIONS`: one line per topic: the document/version in force and the deciding quote. The inventory's `rules.conflicts.md` lists some; the documents win over the inventory.

**Language: the agent speaks the language of the calls** (the language of the example conversations and customer-facing texts, not of the instructions around them), naturally, as a native speaker says it on the phone:
- The system prompt (first line: "you speak only <language>", in that language) and every `task_message` in that language; every tts `on_enter`, terminal farewell, `what_to_do_next` hook text, error, transfer and goodbye line in it; the documents' verbatim lines unchanged. Extraction and transition descriptions may stay in English (never spoken); enum values stay ASCII snake_case.
- The library's texts are English: never `assemble(..., conduct=True)` for another language (PERSONA_CONDUCT quotes English lines the model then says): pass `conduct=False` and write the same conduct rules in the call's language; pass the language's wording wherever a helper takes text (`opening_no_answer(prefix=...)`, hook texts). `CAL_HELPERS.txt()` (English day/month names), `normalise_pre`, `relative_days_code` and `policy.resolve_when` (English number and date words) are English-only.
- Dates: parse `now` in code as local wall-clock time (`datetime.datetime.fromisoformat(raw[:19])`, or `raw[:16]`: keep the time of its offset, never convert to UTC; never the real clock, never `{{system.*}}` dates); write spoken dates in code with the language's own day and month names and word order (a small table in the generator). Amounts: format in code the way the documents and examples write them (that language's thousands and decimal separators, the currency named as a word in that language, never `1234.5 USD`), in the order the examples read them. A zero or missing value gets the documents' sentence for it, never an empty template (an empty variable is spoken as the literal placeholder).
- Caller input: let extraction read the caller's words (the model understands the language) and keep arithmetic in code. Prefer closed choices: code computes the allowed options and speaks them, an enum extraction picks one (`opt1`..`optN`, `none`, `other`). If code must parse free words, write the language's own table in the generator (number words, weekday and month names, relative words in that language) and resolve against `now`; never a `date`-type extraction (it resolves relative words with the real clock).

## Service lines: a small explicit graph on freyalib primitives

```
opening   fl.opening_conv(name, <the documents' greeting>, task, [fl.ext("intent", ...)]): the line as tts AND as the chat
          route's first model turn; the caller's first words often already hold the request: extract it here
  └ always ─> load      fl.api_node(name, fl.api_tool(api, <read tool>, baked={<identity field>: "{{<call variable>}}"}),
                        [fl.always("prepare")], mapping=[{"path": "data.<x>", "variable": "<x>"}])
  └─> prepare  fl.code_node: facts from the mapped results -> finished sentences in the language (<x>_line), `route`
        ├ route == "error" ─> load once more (counter in code) ─> the documents' technical-problem ending
        ├ route == "choose" ─> choose (conv, tts code-built list of the items; enum opt1..optN) ─> select (code) ─> ...
        └─> answer (conv, tts {{answer_line}}; extract `intent`) ─┬ intent == <service> ─> one node (chain) per service action
                                                                 ├ intent == <transfer triggers> ─> transfer ─> end
                                                                 ├ intent == done ─> end (goodbye)
                                                                 └ question / none ─> the model answers (FAQ in the prompt), stays
```
- The initial node is a conversation node (the chat route skips a first code node): `fl.opening_conv(...)`, then set its transitions to `[fl.always("load")]` (or `fl.conversation_first(...)` when the first code node needs no tool result).
- **Tools from the API file** (our own mock: names, paths, methods, fields, enums from the file only). First `fl.CALL_VARS.add("<identity call variable>")` for every call variable a request carries (body field, path, query or header parameter of that name is then baked from `{{<name>}}`: never asked, never model-filled). `fl.tool_names(api)` lists the tools (operationId, else the kit's `POST /<name>`, else the last path segment that is not a parameter); `fl.tool_spec(api, name)` gives method, path, path/query parameters, fields and response properties; `fl.api_tool(api, name, baked=...)` builds any method and path (model-filled path/query parameters are moved into the URL by its pre hook). Read their docstrings in `builder/freyalib.py` once. `close_call_tool` / `end_pair` only when the API has a close tool (outcome/reason from its enums); without one, end with `fl.end_node(name, <descriptive ended_reason>, <farewell>)`.
- **Reads run in `fl.api_node`** (engine-run) with every value baked from a call variable or a variable code set; model-called tools only where the caller's free value must go in (with `fl.what_next_post` in the call's language). Map the response at node level (`data.` paths). Measured on Freya (final-case build, 11 Oct): (1) a tool result is `{"status": "success"|..., "data": <the response body>, "status_code": <http>}`, so when the API's own body has a `data` object a field is at `data.data.<field>` and its result block at `data.result.<field>` (one level too shallow read every answer as empty: "no card" for every caller); (2) a `tts` `on_enter` on an `api_node` broke the chain: keep api nodes silent and speak from the next node; (3) `<tool>_success_count` does not count for a tool run by an `api_node`: route on `<node>_response.status == "success"` (and on the API's own success field); an HTTP error (4xx/5xx) arrives as a non-success status, route it to the documents' error line.
- **Every figure the caller hears is computed in code** from the mapped results and spoken by a tts `on_enter` (or quoted "say exactly" in the prompt): every currency/field the API returns, a zero or missing value, the due date, an item chosen among several (one item: no question; several: a code-built list and an enum choice). The model never adds, converts or rounds a figure.
- **Intent routing on an extracted enum**: one `fl.ext("intent", [<the services the documents allow>, <transfer triggers, e.g. human, pay>, "done", "question", "none"], desc)` on every node where the caller can ask for something; deterministic `fl.eq("intent", v, target, desc)` transitions first; a code node after each action writes `intent = "none"` (an enum value: schema-validated) so a value never routes twice.
- **One node (chain) per service action**: collect its parameters as closed choices computed in code (the documents' limits: allowed values, cut-off days, how often, are code checks with the documents' sentence for a refusal), read back and confirm (`confirm` enum yes/no/change), write in an `fl.api_node` with the confirmed values baked, route on the result (`fl.ok_true`, `fl.tool_failed_twice`, response fields); say it is done only after a success; then back to "anything else?".
- **Transfer**: the documents' triggers route deterministically to one transfer chain: the transfer tool in an `fl.api_node` when the API has one, the documents' transfer sentence as the terminal farewell. A "help first, then transfer" rule is a counter in code (`fl.counter_code`).
- **Every ending** `fl.end_node` with the documents' closing words in the language; every path reaches one; a caller who says they are done gets the goodbye.
- System prompt (in the language): who the agent is (the documents' name), what it can and cannot do, the conduct rules, FAQ answers, "after every tool result speak or call the next tool", never invent a figure, never say an action is done before the tool succeeded.

## Self-tests without practice cases (own mock, no organisers' ledger)

- **Use the whole budget.** Do not finish early while time is left: after the happy paths pass, run the remaining example conversations of the case (every one, the adversarial ones included) and one call per error status the test data contains (each 4xx/5xx answer of each service, a slow answer), then the branches the documents describe that no test has reached (several items with the same name, nothing to read, a write the caller declines, a request outside scope, a caller who asks for a person or to do something only a person can). Fix and save after each failing round; stop only at the deadline or when every listed branch has passed once.

- `builder/sim.py`, `builder/cases.py` and `tools/run_cases.py` need the organisers' mock (`/v1/practice/sessions` + its ledger): they cannot run a call on our own mock. Do not start them; `--close-from-args` does not help.
- Order: generator → `python3 builder/lint.py out/<slot>.workflow.json --api <api> --call-vars <the CALL VARIABLES line, comma-separated> --rules out/<slot>.rules.json --budget` → dry run and save (step 6) → smoke. Save a working agent by about minute 12.
- Expected data: the case folder's test-customer file (its path is in the combined brief) gives each test customer's call variables and data; `curl -s` the mock's read endpoint (the API file's server URL + path) for one of them to see the figures the agent must say.
- **Driven smoke**, one per example-conversation type (read the figures, each service action, pay/human transfer, several items, a zero/missing value, an FAQ question):
  `python3 builder/smoke.py <slot> --vars-only --vars '{"<identity call variable>": "<test customer value>", "now": "<ISO time with the documents' offset>"}' --language <Language> --customer "<persona from one example conversation, with the test customer's facts>" --max-turns 10 --out results/<slot>-smoke/<name>.json`
  `--vars-only` sends exactly these call variables (without it the kit's English defaults go too); `--language` makes the customer model speak that language and open with a bare 'hello?' in it: on the chat route the caller speaks first and the agent answers with its opening line, so the request comes in the second line, as after the greeting on a real call (`--opening "<words>"` sets the first line yourself). At most two runs at a time (the chat route answers 504 under load); 1-3 minutes each.
- **Scripted smoke** for the deterministic paths: `out/smoke/<slot>/<name>.json` with `"variables"` (the test customer's call variables), `"turns"` (lines from the example conversations, in the language) and expectations: `tool: {"name", "count"}` (an `api_node` tool is named by the last non-id segment of its URL, a model-called tool by its function name), `tools_called_any`, `contains_any` with the figures as the agent says them (`re:` for number formats), `not_contains` with `{{` and `re:\b(the|and|your|please)\b` (English leaking). `python3 builder/smoke.py <slot> --script out/smoke/<slot>/<name>.json --vars-only`.
- In every run check: the `[tool]` lines go to the mock's URL with the right identity value and answer HTTP 200 with data; the agent's figures equal the mock's (every currency, the due date in the language); the language never switches; no literal `{{`; routes follow the flow drawing; the transfer and goodbye lines are the documents'. Read each transcript against the example conversations (order, wording, length) as the judge would. Fix the generator, regenerate, lint, save, re-run only what failed.

## Procedure

1. **Read everything.** (A service line: section 0 first.) The brief(s) in full, then the tool API file (every path, field, enum, description, required list), then the rule inventory `out/<slot>.rules.json` and `.md` (made before you started; if absent run `python3 builder/rules.py <briefs> --api <api> --out out/<slot>.rules.json`). Every rule `in_force` must end up implemented somewhere.
   - **Resolve `out/<slot>.rules.conflicts.md` first**: rules only one extraction sample found, values the samples disagree on, values a fresh reader could not confirm from a quote, the dated decisions (which statement is in force, with the deciding quote) and spec problems. For each item re-read the quoted source sentence in the brief and decide; the brief wins over the inventory.
   - **Use `out/<slot>.spec.json`** (schema at the top of `builder/spec_check.py`): calendar, bands with deadline rules, floors, attempt ladder, callback window, identity order, wrong-answer limit, outcomes, note reasons, verbatim lines, forbidden words. Load it in the generator (`json.load`) and pass the values into the setup/prepare code and `end_pair` instead of retyping them; write code from the `text` fallback where a field says `other`. If it has a `timeline`, a decision takes effect during the calls: key the code on `now` (both versions); a close code changed from a date on is `fl.dated(<old>, {"<YYYY-MM-DD>": <new>})` as the `reason` of `end_pair` / `POLICY.end_pair` (chosen in code against the call's date; list every value in the close_call reason description). Check edits with `python3 builder/spec_check.py out/<slot>.spec.json --api <api>`.
2. **Read the references.** `builder/FREYALIB.md` (the library, and its section "Policy as code" on `builder/policy.py`), `out/gen_brief-a_v3.py` (reference generator for a one-product brief) and `out/gen_brief-b_v3.py` (one to three products with notes), both on `builder/policy.py`. They encode ANOTHER bank's rules: take the structure, never the content. (`out/gen_brief-a_lib.py`, `out/gen_brief-b_lib.py` and `builder/MULTIPRODUCT.md` are the older prompt-decided payment flow.)
3. **Design the mapping.** For every rule decide where it lives, and write `# R12`-style comments next to the code:
   - **code node** for anything computable: business days, holidays, deadlines per band, floors, attempt proposals, callback windows, weekday words, counters (wrong answers, refusals, attempts). `next_bd(d)` returns d itself when d is a business day; 'the next business day after the call date' is `bd_after(today)`, 'the business day before d' is `bd_before(d)` (Kestrel: `next_bd(today)` put attempt 1 on the call date). Do all arithmetic in code and hand the model finished facts as text (`{{facts}}`), including a day-by-day calendar with allowed/not allowed per product.
   - **tool definition** from the API: every body field as a leaf with the spec's type/description/enum; bake what the workflow knows (`customer_id`, `field`, `queue`, `outcome`), let the model fill the rest; descriptions say WHEN to call the tool.
   - **transition** for every state change: route on tool results (`ok_true`, counters, `wrong_answers_left`), on extracted enums (`who`, `topic`, `stance`, `confirm`) and on the `route` flag code writes, never on prompt text; deterministic conditions first. No model-judged exit in the payment part (`intent_tool('fin_refused')` is what `policy.py` replaces).
   - **hook** (`what_next_post`, `verify_post`, `promise_post`) so every tool result carries a `what_to_do_next` line in the brief's terms.
   - **prompt sentence** for conduct rules; verbatim sentences go into `on_enter` tts text or the terminal farewell, quoted exactly as the brief writes them.
4. **Write `out/gen_<slot>.py`** with `builder/freyalib.py` (`sys.path.insert(0, 'builder')`). Architecture rules:
   - The **initial node is a conversation node** (the opening). The chat route (used by the local simulator and the smoke tests) skips a first code node; simulations do not. Compute facts in code nodes entered after the first customer turn: `opening` (extract who answered) → `setup` (code, passthrough, routes on `who`) → `ask_<q1>` / `third_party` / `fin_*`. Every code node must be safe to run with partial state (`vars.get`, fallbacks).
   - **A reply with no answer is not one of the brief's identity asks.** Once `opening`, `setup` and the second ask (`opening_retry`, ending with `always` → the unclear ending) are built, call `fl.opening_no_answer(nodes, "<the brief's identity question, e.g. Am I speaking with {{title}} {{last_name}}?>")` (node and variable names are parameters). It adds `no_answer` (only small talk or a line cut off mid-way) to `who1`/`who2` ahead of the catch-all, counts it in code with one fixed re-ask per ask, and makes the second ask always end with the question. Measured on the organisers' simulator (talkative style, extended Brief A EXT-A-08/EXT-A-40): without it, two cut-off small-talk lines closed the call as unclear after ONE identity question, because the system prompt's 'Please go on.' replaced the second ask. Keep greetings, 'go ahead', questions and silence in the brief's catch-all value (they still count as asks).
   - One `ask_<field>` node per identity question, in the brief's order, `api_tool(api, "verify_identity", baked={"field": ...})`, `verify_post` with the API's hint values and the brief's wrong-answer limit. If the brief's limit is stricter than the service's, count wrong answers in a hook or code and route on your own counter.
   - **Speech normalisation**: every identity, promise and callback tool gets `pre=fl.normalise_pre({...})` on its spoken fields (`answer`, `amount`, `date`, `time`) with the brief's date order (`date_order='dmy'|'mdy'`; add `relative_days_code` + `relative_var` when the brief fixes how "next Friday" reads); identity prompts carry `fl.latest_value_note(N)`, and digit answers that are extracted use `fl.digit_extraction(name, N, desc)` (N from the brief/API).
   - **Four lessons from the hidden-path rehearsal (generated cases on Brief A, 14/19)**: when the brief says "first sentence", make the opening ONE sentence (two sentences cost the case); a human request at an identity question is NOT a refusal: give the refusal enum a `human` value routed back to the node with no counter (the prompt asks once whether you can help, then calls the transfer tool); "I don't know the exact day" after your question for the exact day is a vague offer (`offer_kind` vague), never `stance` refuse: say so in both descriptions; "ask once for another time" (third-party callbacks) is `fl.third_party_callback(nodes, task, tools, extraction, transitions, reask_text, "fin_no_callback")` (cb_offer extracted against `{{callback_text}}`, the re-ask counted in code and spoken as the brief's fixed sentence; no model-chosen 'second time outside' exit), and every other once-only ask is a counter in code (`fl.counter_code`), not a prompt sentence.
   - **Someone else answers**: build it with `fl.third_party_callback` whatever the brief's callback rule, with the brief's sentence for a third party as the fixed (tts) entry line and the brief's "say the hours, ask once more" sentence as `reask_text` (the library also hands that sentence to the node's prompt: the extraction misread 18:30 as inside a window closing at 17:00 and the model's own re-ask left the hours out). When the brief says what to do if the person offers to pay or help ("thank them, say no"), add `fl.third_party_offer(nodes, "<the brief's thanks and no, e.g. Thank you, but no.>")` after `conversation_first`: the offer usually comes in the same message as "who is this?", and a fixed entry line cannot react to it (Ashvale and Kestrel PUB-02: the offer was never declined).
   - **Every spoken policy text comes from the brief**: `Policy(texts={...})` refuses to build without the brief's wording for `REQUIRED_TEXTS` (too much / floor line, paid, dispute, hardship, change after recording, human-first, no-talk, recorded, anything-else, vague, after-deadline, weekend-or-holiday, below-floor; plus the multi-product lines). Quote the brief's sentences; never leave a library default in. Unless the brief fixes the date wording of its read-back, also pass `today_when: "today, [date]"` and `tomorrow_when: "tomorrow, [date]"`: a customer who said 'this Friday' on a Friday or 'tomorrow' does not know the call's date and refuses a bare 'today' or a bare date.
   - **Never trust an extracted date for relative words**: the platform's date extraction uses the real clock, not the call's `now`. The policy nodes extract the customer's words (`offer_when`) and resolve them in code; pass the brief's rule for "next <weekday>" as `Policy(weekday_rule=...)`. Any other date a tool needs (callbacks) must come from code-built facts in the prompt, never from a `date`-type extraction.
   - **Side questions on policy turns**: give `Policy(asides={...})` every side question the brief answers (robot/AI, scam, who is calling, what is this about) with the brief's answer; the code prefixes it to the spoken line, because a turn routed through code into a tts line never reaches the dialogue model.
   - **Answer a yes/no side question with the yes or no first**, then the brief's sentence ("Yes, I am <the bank>'s digital assistant."): on the extended Brief A set the simulated customer asked "am I talking to a robot?" again after a bare "I am <the bank>'s digital assistant.", and a question at the second identity ask closes the call as unclear (2 of 2 runs).
   - **A question back at an identity question is not a refusal**: give the refusal enum a `question` value (`fl.QUESTION_ENUM_CLAUSE`), route it to `fl.question_back_node(stage, ask_node, close_node)` (answer, ask again; the second question in a row with no answer counts as the brief's deflection) and put `pre=fl.reset_pre(["question_count_<stage>"])` on the identity tool. Measured: counting every question as a refusal closed 4 of 10 calls under the kit's asks_back style. When the brief counts a question back as declining and says what to explain on a decline, the identity prompt's answer to a question back must carry that explanation too (the question is routed to the question-back path, not the refusal path, so the refusal's explanation is never said otherwise: measured on the extended Brief A set, the agent answered 'I can explain after the security questions' twice and closed without ever saying the questions protect the account).
   - **Speech normalisation**: every identity, promise and callback tool gets `pre=fl.normalise_pre({...})` on its spoken fields (`answer`, `amount`, `date`, `time`) with the brief's date order (`date_order='dmy'|'mdy'`, or `'none'` when the brief fixes no order and says to ask for the month as a word: an ambiguous numbers-only date is then left as said; add `relative_days_code` + `relative_var` when the brief fixes how "next Friday" reads); identity prompts carry `fl.latest_value_note(N)`, and digit answers that are extracted use `fl.digit_extraction(name, N, desc)` (N from the brief/API).
   - **Every spoken policy text comes from the brief**: `Policy(texts={...})` refuses to build without the brief's wording for `REQUIRED_TEXTS` (too much / floor line, paid, dispute, hardship, change after recording, human-first, no-talk, recorded, anything-else, vague, after-deadline, weekend-or-holiday, below-floor; plus the multi-product lines). Quote the brief's sentences; never leave a library default in. Unless the brief fixes the date wording of its read-back, also pass `today_when: "today, [date]"` and `tomorrow_when: "tomorrow, [date]"`: a customer who said 'this Friday' on a Friday or 'tomorrow' does not know the call's date and refuses a bare 'today' or a bare date.
   - **Never trust an extracted date for relative words**: the platform's date extraction uses the real clock, not the call's `now`. The policy nodes extract the customer's words (`offer_when`) and resolve them in code; pass the brief's rule for "next <weekday>" as `Policy(weekday_rule=...)`. Any other date a tool needs (callbacks) must come from code-built facts in the prompt, never from a `date`-type extraction.
   - **Side questions on policy turns**: give `Policy(asides={...})` every side question the brief answers (robot/AI, scam, who is calling, what is this about) with the brief's answer; the code prefixes it to the spoken line, because a turn routed through code into a tts line never reaches the dialogue model.
   - **A question back at an identity question is not a refusal**: give the refusal enum a `question` value (`fl.QUESTION_ENUM_CLAUSE`), route it to `fl.question_back_node(stage, ask_node, close_node)` (answer, ask again; the second question in a row with no answer counts as the brief's deflection) and put `pre=fl.reset_pre(["question_count_<stage>"])` on the identity tool. `QUESTION_ENUM_CLAUSE` lists 'what this is about' as a question that does not count: when the brief names a question as declining (e.g. "asks what the call is about instead of answering"), use `fl.question_clause(["<that question in the brief's words>"])` with values `fl.DEFLECTION_VALUES` and route `deflection` to the same decline counter as `refused` (`count_decline_<stage>`), so one such question plus one refusal reaches the brief's limit. A human request or 'does not want to talk' at an identity question gets its own enum value and route when the brief closes on it. Measured: counting every question as a refusal closed 4 of 10 calls under the kit's asks_back style.

   - **Customers talk like people** (small talk, numbers and dates in two parts, self-corrections, questions back, words for numbers): `fl.assemble(..., conduct=True)` adds the library's conduct lines to the system prompt; append `fl.REFUSAL_NONE_CLAUSE` to every refusal/decline enum description (the brief's own list of what counts goes first) and `fl.PLAN_REQUEST_CLAUSE` to every plan-request enum description. Measured on the organisers' simulator: without these, small talk at a security question closed calls as declined and "how much can I pay instead?" became a transfer.
   - `get_account` in an `api_node`; a `prepare` code node computes per-product facts; the statement of the debt is a tts `on_enter` built in code from the brief's wording.

## Rules

- Never edit the agent on the platform by hand. Change the generator and save.
- `build.py` guards the last repair: `builder/sim.py` records the workflow version each case ran on, and when your final version, re-tested, passed 2 or more fewer of the cases it shares with the version tested before it and none more, that earlier version is saved again after you finish. Test only what is saved (save, then run), never an unsaved file.
- Edits you make to `builder/`, `.claude/skills/` or `tools/` during a build are written to a patch in `out/` and reverted after the export (the saved agent is unaffected). Put everything brief-specific in `out/gen_<slot>.py`; extend the library only brief-agnostically.
- When a tool call fails, the agent must say so. It must never tell the customer something is recorded when it is not.
- A customer that passes once can fail the next time. Prefer rules in routes and code over rules in prompts.
- Keep tool definitions faithful to the API file: a field or enum value the brief mentions but the API lacks does not exist; one the API has but the brief does not mention still must be filled correctly.
- Time: the whole build must finish within the budget in the prompt. Save a working agent early (after step 6), then improve it.
