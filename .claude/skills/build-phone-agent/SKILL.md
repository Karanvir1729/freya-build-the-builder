# Build a phone agent from a brief

You are the builder. Input: one or more brief files, a tool API file (OpenAPI JSON), a slot name, and sometimes a cases file for practice. Output: `out/gen_<slot>.py` (your generator), `out/<slot>.workflow.json` (what it emits), saved on Freya under the slot. Work from the repo root.

Use ONLY what the given brief(s) and tool API file say. Never copy a rule, value, date, name, enum or sentence from another brief, from the reference generators, or from memory. Hidden briefs differ from the kit's in every dimension: identity questions, wrong-answer limits, calendars and holidays, bands and deadline formulas, floors, attempt counts and proposals, outcome/reason tables, verbatim sentences, callback windows, tool fields and enum values. Customers can have one to three products. A brief can be raw material (a mail, a policy extract, a memo that changes it, a code list): a later document overrides an earlier one; apply the rule in force.

## Procedure

1. **Read everything.** The brief(s) in full, then the tool API file (every path, field, enum, description, required list), then the rule inventory `out/<slot>.rules.json` and `.md` (made before you started; if absent run `python3 builder/rules.py <briefs> --api <api> --out out/<slot>.rules.json`). Every rule `in_force` must end up implemented somewhere.
   - **Resolve `out/<slot>.rules.conflicts.md` first**: rules only one extraction sample found, values the samples disagree on, values a fresh reader could not confirm from a quote, the dated decisions (which statement is in force, with the deciding quote) and spec problems. For each item re-read the quoted source sentence in the brief and decide; the brief wins over the inventory.
   - **Use `out/<slot>.spec.json`** (schema at the top of `builder/spec_check.py`): calendar, bands with deadline rules, floors, attempt ladder, callback window, identity order, wrong-answer limit, outcomes, note reasons, verbatim lines, forbidden words. Load it in the generator (`json.load`) and pass the values into the setup/prepare code and `end_pair` instead of retyping them; write code from the `text` fallback where a field says `other`. If it has a `timeline`, a decision takes effect during the calls: key the code on `now` (both versions); a close code changed from a date on is `fl.dated(<old>, {"<YYYY-MM-DD>": <new>})` as the `reason` of `end_pair` / `POLICY.end_pair` (chosen in code against the call's date; list every value in the close_call reason description). Check edits with `python3 builder/spec_check.py out/<slot>.spec.json --api <api>`.
2. **Read the references.** `builder/FREYALIB.md` (the library, and its section "Policy as code" on `builder/policy.py`), `out/gen_brief-a_v3.py` (reference generator for a one-product brief) and `out/gen_brief-b_v3.py` (one to three products with notes), both on `builder/policy.py`. They encode ANOTHER bank's rules: take the structure, never the content. (`out/gen_brief-a_lib.py`, `out/gen_brief-b_lib.py` and `builder/MULTIPRODUCT.md` are the older prompt-decided payment flow.)
3. **Design the mapping.** For every rule decide where it lives, and write `# R12`-style comments next to the code:
   - **code node** for anything computable: business days, holidays, deadlines per band, floors, attempt proposals, callback windows, weekday words, counters (wrong answers, refusals, attempts). `next_bd(d)` returns d itself when d is a business day; 'the next business day after the call date' is `bd_after(today)`, 'the business day before d' is `bd_before(d)` (Kestrel: `next_bd(today)` put attempt 1 on the call date). Do all arithmetic in code and hand the model finished facts as text (`{{facts}}`), including a day-by-day calendar with allowed/not allowed per product.
   - **tool definition** from the API: every body field as a leaf with the spec's type/description/enum; bake what the workflow knows (`customer_id`, `field`, `queue`, `outcome`), let the model fill the rest; descriptions say WHEN to call the tool.
   - **transition** for every state change: route on tool results (`ok_true`, counters, `wrong_answers_left`), on extracted enums (`who`, `topic`, `stance`, `confirm`) and on the `route` flag code writes, never on prompt text; deterministic conditions first. No model-judged exit in the payment part (`intent_tool('fin_refused')` is what `policy.py` replaces).
   - **hook** (`what_next_post`, `verify_post`, `promise_post`) so every tool result carries a `what_to_do_next` line in the brief's terms.
   - **prompt sentence** for conduct rules; verbatim sentences go into `on_enter` tts text or the terminal farewell, quoted exactly as the brief writes them.
4. **Write `out/gen_<slot>.py`** with `builder/freyalib.py` (`sys.path.insert(0, 'builder')`). Architecture rules:
   - The **initial node is a conversation node** (the opening). The chat route (used by the local simulator and the smoke tests) skips a first code node; simulations do not. Compute facts in code nodes entered after the first customer turn: `opening` (extract who answered) → `setup` (code, passthrough, routes on `who`) → `ask_<q1>` / `third_party` / `fin_*`. Every code node must be safe to run with partial state (`vars.get`, fallbacks).
   - **A reply with no answer is not one of the brief's identity asks.** Once `opening`, `setup` and the second ask (`opening_retry`, ending with `always` → the unclear ending) are built, call `fl.opening_no_answer(nodes, "<the brief's identity question, e.g. Am I speaking with {{title}} {{last_name}}?>")` (node and variable names are parameters). It adds `no_answer` (only small talk or a line cut off mid-way) to `who1`/`who2` ahead of the catch-all, counts it in code with one fixed re-ask per ask, and makes the second ask always end with the question. Measured on the organisers' simulator (talkative style, extended Brief A EXT-A-08/EXT-A-40): without it, two cut-off small-talk lines closed the call as unclear after ONE identity question, because the system prompt's 'Please go on.' replaced the second ask. Keep greetings, 'go ahead', questions and silence in the brief's catch-all value (they still count as asks).
   - One `ask_<field>` node per identity question, in the brief's order, `api_tool(api, "verify_identity", baked={"field": ...})`, `verify_post` with the API's hint values and the brief's wrong-answer limit. If the brief's limit is stricter than the service's, count wrong answers in a hook or code and route on your own counter.
   - **Speech normalisation**: every identity, promise and callback tool gets `pre=fl.normalise_pre({...})` on its spoken fields (`answer`, `amount`, `date`, `time`) with the brief's date order (`date_order='dmy'|'mdy'`; add `relative_days_code` + `relative_var` when the brief fixes how "next Friday" reads); identity prompts carry `fl.latest_value_note(N)`, and digit answers that are extracted use `fl.digit_extraction(name, N, desc)` (N from the brief/API).
   - **Four lessons from the hidden-path rehearsal (generated cases on Brief A, 14/19)**: when the brief says "first sentence", make the opening ONE sentence (two sentences cost the case); a human request at an identity question is NOT a refusal: give the refusal enum a `human` value routed back to the node with no counter (the prompt asks once whether you can help, then calls the transfer tool); "I don't know the exact day" after your question for the exact day is a vague offer (`offer_kind` vague), never `stance` refuse: say so in both descriptions; "ask once for another time" (third-party callbacks) is `fl.third_party_callback(nodes, task, tools, extraction, transitions, reask_text, "fin_no_callback")` (cb_offer extracted against `{{callback_text}}`, the re-ask counted in code and spoken as the brief's fixed sentence; no model-chosen 'second time outside' exit), and every other once-only ask is a counter in code (`fl.counter_code`), not a prompt sentence.
   - **Every spoken policy text comes from the brief**: `Policy(texts={...})` refuses to build without the brief's wording for `REQUIRED_TEXTS` (too much / floor line, paid, dispute, hardship, change after recording, human-first, no-talk, recorded, anything-else, vague, after-deadline, weekend-or-holiday, below-floor; plus the multi-product lines). Quote the brief's sentences; never leave a library default in. Unless the brief fixes the date wording of its read-back, also pass `today_when: "today, [date]"` and `tomorrow_when: "tomorrow, [date]"`: a customer who said 'this Friday' on a Friday or 'tomorrow' does not know the call's date and refuses a bare 'today' or a bare date.
   - **Never trust an extracted date for relative words**: the platform's date extraction uses the real clock, not the call's `now`. The policy nodes extract the customer's words (`offer_when`) and resolve them in code; pass the brief's rule for "next <weekday>" as `Policy(weekday_rule=...)`. Any other date a tool needs (callbacks) must come from code-built facts in the prompt, never from a `date`-type extraction.
   - **Side questions on policy turns**: give `Policy(asides={...})` every side question the brief answers (robot/AI, scam, who is calling, what is this about) with the brief's answer; the code prefixes it to the spoken line, because a turn routed through code into a tts line never reaches the dialogue model.
   - **Answer a yes/no side question with the yes or no first**, then the brief's sentence ("Yes, I am <the bank>'s digital assistant."): on the extended Brief A set the simulated customer asked "am I talking to a robot?" again after a bare "I am <the bank>'s digital assistant.", and a question at the second identity ask closes the call as unclear (2 of 2 runs).
   - **A question back at an identity question is not a refusal**: give the refusal enum a `question` value (`fl.QUESTION_ENUM_CLAUSE`), route it to `fl.question_back_node(stage, ask_node, close_node)` (answer, ask again; the second question in a row with no answer counts as the brief's deflection) and put `pre=fl.reset_pre(["question_count_<stage>"])` on the identity tool. Measured: counting every question as a refusal closed 4 of 10 calls under the kit's asks_back style. When the brief counts a question back as declining and says what to explain on a decline, the identity prompt's answer to a question back must carry that explanation too (the question is routed to the question-back path, not the refusal path, so the refusal's explanation is never said otherwise: measured on the extended Brief A set, the agent answered 'I can explain after the security questions' twice and closed without ever saying the questions protect the account).
   - **Speech normalisation**: every identity, promise and callback tool gets `pre=fl.normalise_pre({...})` on its spoken fields (`answer`, `amount`, `date`, `time`) with the brief's date order (`date_order='dmy'|'mdy'`, or `'none'` when the brief fixes no order and says to ask for the month as a word: an ambiguous numbers-only date is then left as said; add `relative_days_code` + `relative_var` when the brief fixes how "next Friday" reads); identity prompts carry `fl.latest_value_note(N)`, and digit answers that are extracted use `fl.digit_extraction(name, N, desc)` (N from the brief/API).
   - **Every spoken policy text comes from the brief**: `Policy(texts={...})` refuses to build without the brief's wording for `REQUIRED_TEXTS` (too much / floor line, paid, dispute, hardship, change after recording, human-first, no-talk, recorded, anything-else, vague, after-deadline, weekend-or-holiday, below-floor; plus the multi-product lines). Quote the brief's sentences; never leave a library default in. Unless the brief fixes the date wording of its read-back, also pass `today_when: "today, [date]"` and `tomorrow_when: "tomorrow, [date]"`: a customer who said 'this Friday' on a Friday or 'tomorrow' does not know the call's date and refuses a bare 'today' or a bare date.
   - **Never trust an extracted date for relative words**: the platform's date extraction uses the real clock, not the call's `now`. The policy nodes extract the customer's words (`offer_when`) and resolve them in code; pass the brief's rule for "next <weekday>" as `Policy(weekday_rule=...)`. Any other date a tool needs (callbacks) must come from code-built facts in the prompt, never from a `date`-type extraction.
   - **Side questions on policy turns**: give `Policy(asides={...})` every side question the brief answers (robot/AI, scam, who is calling, what is this about) with the brief's answer; the code prefixes it to the spoken line, because a turn routed through code into a tts line never reaches the dialogue model.
   - **A question back at an identity question is not a refusal**: give the refusal enum a `question` value (`fl.QUESTION_ENUM_CLAUSE`), route it to `fl.question_back_node(stage, ask_node, close_node)` (answer, ask again; the second question in a row with no answer counts as the brief's deflection) and put `pre=fl.reset_pre(["question_count_<stage>"])` on the identity tool. `QUESTION_ENUM_CLAUSE` lists 'what this is about' as a question that does not count: when the brief names a question as declining (e.g. "asks what the call is about instead of answering"), use `fl.question_clause(["<that question in the brief's words>"])` with values `fl.DEFLECTION_VALUES` and route `deflection` to the same decline counter as `refused` (`count_decline_<stage>`), so one such question plus one refusal reaches the brief's limit. A human request or 'does not want to talk' at an identity question gets its own enum value and route when the brief closes on it. Measured: counting every question as a refusal closed 4 of 10 calls under the kit's asks_back style.

   - **Customers talk like people** (small talk, numbers and dates in two parts, self-corrections, questions back, words for numbers): `fl.assemble(..., conduct=True)` adds the library's conduct lines to the system prompt; append `fl.REFUSAL_NONE_CLAUSE` to every refusal/decline enum description (the brief's own list of what counts goes first) and `fl.PLAN_REQUEST_CLAUSE` to every plan-request enum description. Measured on the organisers' simulator: without these, small talk at a security question closed calls as declined and "how much can I pay instead?" became a transfer.
   - `get_account` in an `api_node`; a `prepare` code node computes per-product facts; the statement of the debt is a tts `on_enter` built in code from the brief's wording.
   - **The payment part is policy as code (`builder/policy.py`, the default architecture).** Every rule whose outcome can be computed from the call variables, tool results and extracted enums is decided in code or a route; a prompt only phrases what code decided. `POLICY = pol.Policy(holidays, texts={...the brief's sentences...}, multi=..., notes=..., note_reasons=..., fin_keys=...)`, then:
     - `prepare = POLICY.prepare_code(body, "statement")`: per product `register_product(vars, pid, words, full, floor, floor_name, deadline, rungs)` with the brief's band, floor, deadline and persuasion ladder (`rungs`, amount rules `full` / `floor` / `full_or_floor` = the floor once the customer said the full amount is too much), and the statement of the debt.
     - **negotiate → check_offer → confirm**: `POLICY.negotiate_node(task, [topic, stance, (offer_for,) offer_kind/date/amount], topic_transitions() + offer_guard_transitions() + stance_transitions())`. Every customer offer goes through the guard (weekend/holiday, after the deadline, below the floor, above the full amount, before today, vague), every agent offer is a code-built sentence from the ladder; enum descriptions quote the brief's own definitions (a proposed date or amount is never a refusal; 'too much' is not a plan request).
     - **Counters in code**: refusals per product (`attempts_used_<pid>`, exhausted → the refused ending or the product's note), the floor offered once, 'does not want to talk' twice, a human request asked once then transferred; hardship routes to `hardship_node`, where no offer is proposed (routing) but a named offer still goes through the guard. Every persuasion offer (each ladder rung, the floor) and the support team are spoken once by code; `negotiate_node` / `hardship_node` append `ONCE_RULE` and the state line marks an offer already spoken 'already said once', so never write a prompt line that tells the model to ask the offer again: write "then follow STATE for what to ask" (`negotiate_node` rewrites "then ask the current offer again" anyway). Measured on Freya: talkative customers got the support team three times and the floor twice, and a 'No.' after small talk that was not extracted got attempt 1 again word for word, which the judge counted as a third attempt on a two-attempt product (EXT-B-01).
     - **confirm**: `POLICY.confirm_node(...)`, read-back built in code (the brief's confirmation question), `change` → guard → read back again, never a transfer; `POLICY.record_nodes(nodes, api)` writes in an `api_request` node with the read-back values baked and asserted, retries as the brief says.
     - **What one turn can carry** (extended practice sets, all handled in `policy.py` once wired): an amount by reference ('the minimum': pass the brief's names for its floor as `ref_desc=` to `offer_extraction`, `confirm_node` and `hardship_node`); 'too much, but I can pay on <day>'; 'I can't do Friday, but I can pay it in full' (`day_refused`, part of `offer_extraction`: the exact-day question, never the declined day); a paid/dispute claim that names a product already settled (settles only live products and never restarts the product on the table; `offer_for` positions follow the statement's order, so describe it that way, not 'in the order of the agent's latest line'); different claims and days for different products in one answer (`per_product`, automatic with `multi=True`). If the brief adds no notes on a call that ends in a transfer, pass `Policy(notes_on_transfer=False)`.
     - **Wrap-up after a recorded promise**: `POLICY.wrapup_node(...)` speaks the recorded sentence and the brief's after-promise sentence, then gives the customer their next turn (nothing → promise ending; human → ask once, transfer; plan → restructuring; change → the brief's change sentence, promise unchanged; question → answer).
     - **Read every Policy parameter off the brief** (`builder/policy.py` class docstring), not off the reference generator: `business_weekdays`, `weekday_rule` (the weekday words: 'this_week', 'first_after', 'first_after_plus7' when a bare or 'this' <weekday> is the first one after today and 'next' is seven days later, or 'first_from_today' when 'next' <weekday> is the first one after today and 'this' <weekday> said on that weekday is today), `closed_day_move`, `fail_max` (the first write + the retries the brief allows), `human_limit` (1 when the brief says transfer at once / do not ask first), `notalk_limit` (1 when it says end at once), `vague_again` ('refuse' when no exact day after the one ask counts as a non-answer, 'deadline' when the brief proposes the deadline, 'week_end' when it proposes the last business day of the current week), `above_full` ('agree' when the brief says record the full amount), `promise_reasons` (when the promise ending's reason depends on full vs partial), `targets` (e.g. `{"xfer_restructuring": "<ask node>"}` when the brief asks before connecting). A `fin_keys` value may name a transfer `api_node` called `fin_<key>` (e.g. a dispute that the brief transfers) that then routes to its ending. When the brief says a promise recorded earlier decides the ending over a later transfer, build every ending with `POLICY.end_pair(...)` (its fin node runs `POLICY.ending_code`). The reference generators' values are another bank's: Brief C's transfer test found five parameters where Brief A's value would have been wrong.
     - **`{{state_line}}` first** in every negotiation, confirm, hardship and wrap-up prompt (`POLICY.state_first`); `POLICY.add_event_nodes(nodes)` adds the policy code nodes. Unit-test the prepare and event code by exec with sample `vars` (see `builder/tests/test_policy.py`) before saving.
   - **Multi-product whenever the brief allows more than one product** (`Policy(multi=True)`): per-product band/deadline/floor/attempts, one question for all first, then one-by-one in the brief's order, one read-back for all, `add_note` per product without a promise when the brief uses notes (`notes=True`, reasons from the API's enum), the closing outcome by the brief's precedence (`fin_keys`; the `finalize` policy node). Build it even when the practice cases happen to have one product. If the brief's read-back or ordering rules differ from what `policy.py` does, extend the module (brief-agnostically) rather than falling back to prompt rules.
   - One `end_pair(key, outcome, reason, farewell)` per row of the brief's outcome/reason table, farewell with the brief's verbatim closing words; `close_call_tool(api, ...)` as the `end_of_call` lifecycle tool, enum from the API. A customer can hang up before any `fin_*` node runs: write a default `outcome`/`reason` per phase in code (in `setup` from the opening answer, in `prepare` after verification) from the brief's own row for "does not want to talk / ends the call", so `close_call` never goes out empty (the audit flags it).
   - Say "recorded" only after `ok` true; retries exactly as the brief says; never end a turn without speaking or calling the next tool (put this in the system prompt).
   - **Never emit `test_variables`** (`assemble(..., test_variables=None)` or leave it out). On the chat route the tool bodies of conversation nodes take `customer_id` from `test_variables` instead of the call, so every bank call fails; without `test_variables` the real id is used (verified) and simulations are unaffected.
   - `assemble()` must pass; no `null`, no `{{` in code, booleans tested both spellings, every passthrough ends with `always`, every path reaches an end node.
5. **Generate and check locally.** `python3 out/gen_<slot>.py <api>`; `python3 builder/lint.py out/<slot>.workflow.json --api <api> --call-vars <the call variables the brief lists, e.g. customer_id,first_name,last_name,title,now> --rules out/<slot>.rules.json --budget` (fix every ERROR, read every WARN; without `--call-vars` a workflow shipped without test_variables gets one false warning per call-variable placeholder). Unit-test the date/amount code: execute the setup and prepare snippets locally with `vars` for two or three example products and the brief's `now`, print the facts, and compare with your own hand calculation from the brief (deadline per band, floor, attempt dates, callback window). Fix until they agree. `--rules` checks the workflow against the inventory (builder/LINT.md): every verbatim sentence must be fixed text, not a prompt line; the forbidden words before verification must not appear in pre-verification speech; a write tool reachable before verification gets a WARN to check against the brief; 'recorded'/'confirmed' must never be said before `ok: true`; `--budget` flags task_messages over 2500 characters (move facts into code-built text, deciding rules first).
6. **Dry-run and save.** `python3 -c "import freya,json,sys; wf=json.load(open(sys.argv[2])); freya.validate_workflow(sys.argv[1], wf); print(json.dumps(freya.save_workflow(sys.argv[1], wf)))" <slot> out/<slot>.workflow.json` prints `workflow_id` and `agent_id`. The same slot updates the same workflow.
7. **Smoke.** Sequentially: `python3 builder/smoke.py <slot> --script builder/smoke_scripts/opening.json`, then `third_party.json`, then `wrong_number.json` (generic checks any collections brief must pass; adapt expectations only where this brief's wording differs: the scripts expect the kit bank's name in the opening, so copy them to `out/smoke/<slot>/` with the brief's bank name). The smoke `customer_id` is not a mock customer: a bank tool answering `unknown customer_id` there is expected; check the request body instead. Then the two persona scripts on a practice customer whose identity passes (a happy-path case of the practice set, or of `out/<slot>.cases.json` with `--cases` for a brief without one): `python3 builder/smoke.py <slot> --script builder/smoke_scripts/talkative.json --case <id> --practice` and the same with `asks_back.json` (small talk before each answer and a cut-off line at the second security question; 'why do you need that?' at a security question and 'which account is this about?' at the first payment question). They assert `verify_identity` is called once per question with the case's value, `get_account` after identity, no close, transfer or promise on small talk or a question back, and no sympathy sentence for small talk. If the brief asks other security questions than the practice case's identity block in that order, pass `--answers '["<first>", "<second>"]'`. Fix failures in the generator.

8. **Audit.** `python3 builder/audit.py --rules out/<slot>.rules.json --workflow out/<slot>.workflow.json --generator out/gen_<slot>.py --out out/<slot>.audit.json`. Fix every `contradicted` and `missing` rule and the `top_fixes`; regenerate, lint, save. Audit again if time allows.
9. **Practice cases, only when a cases file was given.** `python3 builder/sim.py <slot> --cases <file> --concurrency 3` (the chat route answers 504 above that) (local, parallel, needs OPENAI_API_KEY or falls back to the Claude CLI), or `python3 tools/run_cases.py <agent_id> --cases <file>` when the prompt says to use the organisers' simulation (one at a time, 3-11 minutes, run in the foreground and wait). Read every FAIL reason and the transcript; fix the generator (never the platform by hand); regenerate, save, rerun. At most three rounds. Stay inside the time budget given in the prompt.

   **Generated cases (no organisers' cases: hidden briefs).** The prompt then names `out/<slot>.cases.json`, written from the brief by an independent case writer (`builder/cases.py`); its expectations can be wrong. Never open `out/<slot>.cases.rationale.md`, and never edit the cases file. Repair round, at most 2 rounds, each only when at least 6 minutes of the budget are left:
   1. Save first (step 6), so a working agent exists whatever happens. If the test bank answers `close_call` with "this outcome needs one of these reasons" (its table does not know this brief's codes), add `--close-from-args` to the sim command: the outcome and reason the agent sent are scored instead. Then pick the cases to run so that a repair round fits: all identity and promise cases with high `expected_confidence` first (about 10 cases, `--only`), the rest only if time remains.
   2. `python3 builder/sim.py <slot> --cases out/<slot>.cases.json --concurrency 2 --out results/<slot>-gen.json --transcripts results/<slot>-gen/` (one rep; the chat route gives 504s above concurrency 2). Budget it: about 45 s per case at concurrency 2 on the OpenAI customer (20 cases = 8 minutes), two to three times slower on the Claude CLI; start it with at least 12 minutes left and NEVER wrap it in `timeout` (a killed run writes no summary and no `--out`; in the cloud rehearsal that cost the whole repair round). Run it in the background and poll the `--out` file, or run it in the foreground with a Bash timeout of at least 20 minutes. If a run is cut off anyway, salvage the `# RESULT` lines from the transcripts.
   3. For every FAIL read the transcript (`results/<slot>-gen/<id>.txt`: lines, tool calls in place, the ledger) and map the failure to a rule id of the inventory (the case's `rule_ids` say which rules it tests).
   4. Fix the generator ONLY when the failure is a deterministic agent error visible in the engine events or tool calls: a wrong route (the node the agent went to contradicts the rule), a missing or wrongly filled tool call (wrong field, enum, product id, `close_call` outcome/reason the routes chose), a wrong fact in a code-built line (date, deadline, floor, weekday, callback slot computed by your code), a hook that throws, a verbatim line missing. Check the claim against the brief yourself before changing anything.
   5. Do NOT change the agent when the case's `expected_confidence` is `low` or `medium` and the disagreement is about that expectation, when the agent's behaviour follows the brief and the expectation does not, or when the customer simulator went off script (said something the script did not say, hung up early). Write those down for the final line instead.
   6. Regenerate, lint, save, and rerun only the cases you fixed (`--only`). Stop at 2 rounds or when the budget is short.
10. **Finish** with one line: `workflow_id`, `agent_id`, number of nodes and tools, the last test result (for generated cases: passed, fixed, and failures left unfixed because the expectation was uncertain), and any rule you could not implement (say which and why).

## Rules

- Never edit the agent on the platform by hand. Change the generator and save.
- `build.py` guards the last repair: `builder/sim.py` records the workflow version each case ran on, and when your final version, re-tested, passed 2 or more fewer of the cases it shares with the version tested before it and none more, that earlier version is saved again after you finish. Test only what is saved (save, then run), never an unsaved file.
- Edits you make to `builder/`, `.claude/skills/` or `tools/` during a build are written to a patch in `out/` and reverted after the export (the saved agent is unaffected). Put everything brief-specific in `out/gen_<slot>.py`; extend the library only brief-agnostically.
- When a tool call fails, the agent must say so. It must never tell the customer something is recorded when it is not.
- A customer that passes once can fail the next time. Prefer rules in routes and code over rules in prompts.
- Keep tool definitions faithful to the API file: a field or enum value the brief mentions but the API lacks does not exist; one the API has but the brief does not mention still must be filled correctly.
- Time: the whole build must finish within the budget in the prompt. Save a working agent early (after step 6), then improve it.
